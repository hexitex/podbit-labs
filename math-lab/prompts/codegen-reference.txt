## Mathematical Verification (mpmath + sympy available)

When verifying mathematical identities, series, integrals, or constant relationships:

### High-Precision Numerical Verification (mpmath)
- `from mpmath import mp, mpf, pi, e, euler, zeta, gamma, catalan, identify, quad, nsum, inf, log, sqrt, power`
- Set `mp.dps = 500` (or higher) for arbitrary-precision arithmetic

- Use `mpmath.identify(value)` for PSLQ integer relation / constant recognition
- For definite integrals: `mpmath.quad(f, [a, b])`
- For infinite series: `mpmath.nsum(f, [1, mpmath.inf])`
- For products: `mpmath.nprod(f, [1, mpmath.inf])`
- Compare with tolerance: `abs(computed - expected) < mpf('1e-100')`

### Symbolic Proof (sympy)
- `from sympy import symbols, simplify, Sum, Product, oo, pi, zeta, bernoulli, factorial, Rational, S`
- Symbolic proof is STRONGER than numerical — it proves exactly, not approximately
- Use `simplify(expr1 - expr2) == 0` for identity verification
- Use `Sum(f, (n, 1, oo)).doit()` for closed-form series evaluation
- Use `limit(expr, x, value)` for limit verification

### Choosing Evaluation Mode
- **numerical**: when comparing computed vs expected values (series sums, integral values, constant identities). Use this when the claim says "X = Y", "X converges to Y", or "X can be expressed as Y" — compute BOTH sides and compare.
- **boolean**: when verifying a true/false mathematical property (divisibility, primality, symbolic identity)
- **convergence**: ONLY when the claim is purely "does X converge?" with NO target value. Output must be `result = {"series": [partial_sum_1, partial_sum_2, ...]}`. Do NOT use convergence mode when the claim specifies WHAT the series converges TO — use numerical mode instead.
- **pattern**: when checking structural properties (symmetry, group structure, mapping properties)

CRITICAL: "Series X converges to a value involving polylogarithms/pi/zeta" is a NUMERICAL claim, not a convergence claim. You must compute the series value AND the expected closed form, then compare them.

CRITICAL — Compound claims require linking tests:
- If the claim has the structure "A causes/enables/implies B", at least one test MUST span the link between A and B
- Testing A alone and B alone does NOT verify "A causes B"
- If no linking test can be constructed computationally, state this explicitly and cap confidence at 0.15

### Claim Type Classification

### Testability Gate (MANDATORY — evaluate BEFORE writing any code)

Before generating verification code, classify the claim's testability:

**LEVEL 1 — Computationally Provable:**
The claim is a mathematical statement that can be verified by exhaustive enumeration, symbolic proof, or high-precision numerical computation from first principles.
Examples: "Boolean rank of K₄ incidence matrix = 4", "This series converges to π²/6", "This recurrence produces these specific integers."
→ Generate full verification code. Confidence can reach 0.95.

**LEVEL 2 — Computationally Testable (consequences):**
The claim makes a prediction whose CONSEQUENCES can be tested computationally, even if the claim itself is about a physical/empirical system.
Examples: "This threshold formula predicts instability above x=3.7" → you can verify the formula's mathematical properties, check dimensional consistency, test edge cases.
→ Generate code that tests consequences. Cap confidence at 0.70. State explicitly which aspect is being tested and which requires empirical validation.

**LEVEL 3 — Empirically Verifiable Only:**
The claim asserts that a physical system behaves in a specific way. No amount of computation can verify it without experimental data. The mathematics may be internally consistent, but internal consistency is not verification.
Examples: "EUV resist shows KPZ dynamics with z ≈ 1.6", "Neural networks undergo martensitic phase transitions", "This material exhibits spinodal decomposition at T > 500K."
→ DO NOT generate verification code that tests internal consistency of the claimed model.
→ Instead return:

```python
    "explanation": "Claim is empirical — asserts physical system behaviour that requires "
                   "experimental data to verify. Mathematical structure of claimed model "
                   "is internally consistent but this does not constitute verification. "
                   "Computational verification not applicable.",
    "testability": "empirical_only",
    "experimental_predictions": [

    ]

```

**LEVEL 4 — Untestable (qualitative analogy):**
The claim draws a qualitative parallel between domains without making any specific quantitative prediction.
→ Return confidence 0.10 with "qualitative analogy — no computational test applicable."

**Classification question:** "If I had unlimited compute but ZERO experimental data, could I determine whether this claim is true or false?"
- YES → Level 1 or 2
- NO → Level 3 or 4

**Anti-patterns that indicate circular verification (REJECT if Level 3):**
1. Generating synthetic data FROM the claimed model, then fitting the claimed model to it
2. Checking if a claimed constant is "close to" a known constant (proximity is not derivation)
3. Checking if a formula produces "physically reasonable" outputs for chosen parameters
4. Verifying that a power law is linear on a log-log plot (true by definition)
5. Checking if a claimed exponent falls within a "valid range" of known exponents
6. Testing dimensional consistency alone (necessary but never sufficient)
7. Asserting an equivalence in a code comment and then only verifying one side (e.g., commenting "C_Wyner = I(Y1;Y2) for DSBS" then only computing I(Y1;Y2) and reporting C_Wyner as verified). If the claim contains an equality A = B and your code computes A but assumes A = B without testing it, you have verified A, not B. The explanation must state which quantity was actually computed and which equivalence was assumed.
